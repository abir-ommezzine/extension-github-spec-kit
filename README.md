# Jira Agent (Kanban Ticket Sync)

> **Naming note**: there is no component literally named "jira agent" in the code. This document covers the ticket/Kanban sync subsystem — the automated pipeline that keeps a Jira-style board in sync with what Copilot is doing in the child project.

## What it does

While Copilot implements tasks from `tasks.md` in a child project, this subsystem keeps a live board (Kanban: **To Do / In Progress / Done**) in sync automatically, with no manual ticket management. Three things happen continuously:

1. **Ingestion** — `tasks.md` is parsed into one ticket per task (`T001`, `T002`, ...). Titles, descriptions and checkbox display state stay in sync with the file.
2. **Status sync** — as Copilot works, it reports progress via a JSON file. A backend watcher picks up every change and promotes ticket status in the database.
3. **Display** — the frontend Kanban board reads ticket status from the database and renders the columns.

The critical rule to remember: **ingestion and status sync are two separate, independent paths.** Ingestion never changes a ticket's status — only the status-sync path can.— see [Status rules](#status-rules) below.

## `current-task.json` contract

Copilot writes this file **before** starting a task (`status: "in_progress"`) and **after** finishing it (`status: "done"`). Every write includes a full snapshot of *every* task's status, not just the one being worked on — this is what lets the board catch up correctly if the backend wasn't running for part of the session (only the last file write is ever visible; without the full map, everything before it would be lost).

```json
{
  "task_id": "T004",
  "file": "src/routes.py",
  "status": "in_progress",
  "project_name": "001-cli-todo-manager",
  "updated_at": "2026-08-11T10:30:00.000000+00:00",
  "tasks": {
    "T001": "done",
    "T002": "done",
    "T003": "done",
    "T004": "in_progress",
    "T005": "todo"
  }
}
```

On each change to this file, `_sync_current_task_to_db()`:
1. Updates the ticket named by the top-level `task_id`/`status` (kept for backward compatibility / quick single-task updates).
2. Iterates the `tasks` map and bulk-applies every entry in it, via `_find_ticket_for_task()` (project-scoped match → path-similarity match → global fallback) and `update_ticket_status()`.

## Status rules

- **`POST /ingest`** (and the frontend's "Ingest Tasks" button / auto-ingest on project select) **never sets a ticket to `in_progress` or `done`.** New tickets are created as `todo`; existing tickets only get their title/description/`checkbox_state`/hash refreshed from `tasks.md`. Checkbox state (`[x]` in the markdown) is stored for **display only** and never drives status.
- **Only `current-task.json`**, read by the backend watcher, can move a ticket forward.
- If tickets are stuck in `todo` despite `tasks.md` showing checked boxes: check that `.task_runtime/current-task.json` exists, is valid JSON, and contains an up-to-date `tasks` map — not that ingestion ran.
- `POST /tickets/{id}/status` (drag-and-drop on the board) and `POST /commit-refine` (infers status from a commit message referencing `T0xx`) also go through `update_ticket_status()` and work independently of the file-watch path.

## API reference

All routes are prefixed `/api/v1` (mounted in `backend/app/main.py`).

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/tickets?project_name=&status=` | List tickets, optionally filtered |
| `GET` | `/tickets/{ticket_id}` | Get one ticket |
| `PATCH` | `/tickets/{ticket_id}/status` | Explicit status update (`{"status": "todo"\|"in_progress"\|"done"}`) |
| `POST` | `/tickets/{ticket_id}/comments` | Add a comment |
| `GET` | `/tickets/{ticket_id}/comments` | List comments |
| `GET` | `/tickets/{ticket_id}/events` | List status-change events (audit trail) |
| `GET` | `/tickets/{ticket_id}/doc-pdf` | Stream the latest generated PDF for the ticket's linked artifact, if any |
| `POST` | `/ingest` | Parse `tasks.md` into tickets (`{"tasks_dir": "...", "project_name": "..."}` — either field can be omitted; see resolution order below) — **never changes status** |
| `POST` | `/commit-refine` | Infer status transitions from a commit message (`{"commit_message": "...", "project_name": "..."}`) |
| `GET` | `/progress?project_name=` | `{total, done, in_progress, todo, progress_pct}` |
| `POST` | `/sync-current-task` | Manually re-run `_sync_current_task_to_db()` — same effect as the file watcher firing, useful when the watcher missed a change or for debugging |

`/ingest` resolves the directory to scan in this order: explicit `tasks_dir` → the parent folder of the project's most recent uploaded `Artifact` (a temp-storage path from the document-upload pipeline, not the live child project) → `backend/specs/<project_name>` under the source repo. Neither of the fallbacks is the live child project's `specs/` folder — keep this in mind if `tasks.md` was edited after the last document upload; the ingested content can be stale relative to what's actually on disk in the child project.

## Data model

- **`Ticket`** — `id`, `project_id`, `artifact_id`, `ticket_id` (e.g. `T004`), `title`, `description`, `status` (`TicketStatus`: `todo` / `in_progress` / `done`), `source_file_path` (`<tasks.md path>#T004`), `source_file_hash`, `checkbox_state` (`checked` / `unchecked` / `in_progress`, display only), `line_number`.
- **`TicketEvent`** — audit trail per status change / comment. Columns: `event_type` (`TicketEventType`), `author_type` (`AuthorType`: `human` / `agent`), `old_status`, `new_status`, `comment`, **`event_metadata`** (JSONB — not `payload`; see gotcha below).
- **`TicketComment`** — free-text comments, human or agent-authored.

## Known gotchas

- **`TicketEvent` has no `payload` column** — the JSONB field is named `event_metadata` (renamed from `metadata`, which is reserved by SQLAlchemy's declarative base). Constructing `TicketEvent(..., payload={...})` raises `'payload' is an invalid keyword argument for TicketEvent` and silently aborts the status update. If you see this error, `ticket_ingestion.py` (or whatever code creates the `TicketEvent`) is out of date — every `TicketEvent(...)` construction and the `TicketEventResponse` read path must use `event_metadata`.
- **Enum name vs. value mismatch** — SQLAlchemy's `Enum` column sends a Python enum member's `.name` to Postgres by default, not `.value`. `ArtifactType.data_model = "data-model"` has a name/value mismatch, so every `SAEnum(...)` column in `models.py` must pass `values_callable=_enum_values` (maps to `.value`) or inserts fail with `invalid input value for enum ..._enum`.
- **Multiple backend clones** — if the child project's `backend/` folder is a symlink/junction, verify it points at the clone you're actually editing. A link pointing at a stale clone will silently serve old code with none of your changes applied, no error shown. See the main `README.md` §3.1 for how the backend is actually resolved.

## Manual testing

```bash
# Ingest tasks.md for a project (creates/refreshes tickets, status untouched)
curl -X POST http://127.0.0.1:8000/api/v1/ingest -H "Content-Type: application/json" \
  -d '{"project_name": "001-cli-todo-manager"}'

# Check board state
curl "http://127.0.0.1:8000/api/v1/progress?project_name=001-cli-todo-manager"
curl "http://127.0.0.1:8000/api/v1/tickets?project_name=001-cli-todo-manager"

# Force a re-sync from current-task.json (same effect as the file watcher firing)
curl -X POST http://127.0.0.1:8000/api/v1/sync-current-task

# Manually move a ticket (bypasses the file-watch path entirely)
curl -X PATCH http://127.0.0.1:8000/api/v1/tickets/<ticket_id>/status \
  -H "Content-Type: application/json" -d '{"status": "done"}'
```
